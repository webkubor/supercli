# 本仓交付与社区投稿审核

不启用自动审核、自动批准或自动合并。GitHub 承载投稿与评论，维护者在本地审核与预览。

## owner 发起的改动

owner 自己的项目改动通过本地 `pnpm build` 和必要的真实浏览器验收后，直接合入 main，不要求创建 PR，也不等待 PR 审核。执行方可按 owner 授权完成合并；若已有 PR，可直接合并。main 更新后跟进部署并核验线上提交及关键交互。以下 PR 审核流程适用于社区外部投稿。

### 浏览器验收清单（视觉/样式类改动必过）

> 教训来源：0.7.0 重设计三连返工——删 theme.css 连带删掉活规则、合并漏断点、新交互类名写岔，
> 全部推上生产后才被用户一句"你自己看过吗"逼出来。此清单就是把那次学费固化成流程。

1. **主题矩阵跑满**：浅色与深色各截一遍关键区块。深色不是浅色的补集——
   字标/图标/描边有独立的深色资产规则（wordmark-dark、暗底衬底、弹窗描边），
   浅色验收通过不代表深色没坏，反之亦然。验收浏览器若固定一种系统偏好，
   另一路径必须用 `data-theme` 强制或换干净上下文补测，不许只测一半。
2. **视口矩阵跑满**：390 / 768 / 1280 / 1600 各测一次 `document.scrollWidth <= 视口宽`。
   页面级溢出和容器内横向滚动要区分开（分类条内部滚动是特性不是 bug）。
3. **新写的交互当场点一遍**：本轮新增的每个可交互元素，真实点击/键入并截图取证成功态，
   不靠"代码看起来对"。类名、data 属性这类手写协调点最易写岔。
4. **读截图描述里的形容词**："faint / 看不清 / 隐约"不是文风，是 bug 线索。
5. **删 CSS/TS 文件前先列清单**：被删文件里每条仍被引用或主动应用的规则（含
   `:root[...]` 条件规则——它们没有"引用方"，按选择器命中排查）逐条迁移或明确放弃，
   不整文件删掉赌里面没有活规则。大文件合并同理：diff 对拍原文件选择器集合。
6. **push 前卫生检查**：`grep -rE '<<<<<<<|>>>>>>>' --exclude-dir=node_modules .`
   必须零命中；测试门禁不覆盖 CHANGELOG/文档，冲突残留靠这一条兜底。

## 投稿人

Fork 后编辑 data/catalog.json；写清官方文档、用途、安装方式与图标来源。没有公开仓库的 CLI 也可以投稿，不编造 Star 数据。个人内部脚本先标记为本地工具，公开前确认没有敏感信息。

## 维护者审核

1. 阅读 PR 的用途与官方来源。核对是否为真实 CLI，避免网页、SDK、同名镜像、失效链接。
2. `gh pr checkout <编号>` 到独立 worktree，检查 diff；不直接执行投稿里的安装脚本。
3. 核对厂商图标、许可证与官方安装文档；有条件时在隔离环境安装 / 执行无副作用的 --help、--version。记录实际验证范围，未试跑不声称已验证。
4. 手动运行 `pnpm check`、`pnpm build`，运行 `pnpm dev` 在页面检查搜索、分类、排序、详情和窄屏。
5. 在 PR 留下“通过 / 需修改”结论，说明证据与限制。确认通过后由维护者手动合并，禁止自动合并。
6. 合并 main 后由 Actions 自动构建、部署并验证线上提交；失败时检查工作流日志，修复后手动重跑。PR 审核与合并仍由维护者决定。

## 数据更新

维护者在本地运行 `pnpm sync`，检查快照差异再提交。GitHub / GitLab 以外的 CLI 无可比 Star 数据，展示“未计分”，排在有指标条目后；绝不填 0 冒充已查询结果。

## 社区投稿收尾

按 [社区维护流程](COMMUNITY.md) 核对 `data/community.json` 收录时间、出处及推荐者的署名选择。信息修改不刷新旧收录时间；已合并但未上线不得提前标“已收录”。Issue 表单先由 GitHub 登录，不接本站 OAuth。

## 对外公开核验范围

公开标准见 https://supercli.site/standards。`data/reviews.json` 仅存有可追溯审核依据的专项记录，不批量为历史工具生成通过标记。每条记录绑定当时名称、维护方、来源分类、用途、仓库、文档与安装命令；这些字段变更后应复核并更新记录，或撤下旧记录。

`checks.method=documentation` 表示资料核对；`execution` 仅用于独立安装实测，必须提供实际环境、工具版本、依据和说明。不能把投稿者自述、本站构建测试或 Scorecard 仓库报告写成本站安装实测。核验者署公开审核记录中的身份；记录本身和卡片展示都要区分来源、核验与热度。

首条 DYT 记录对应 PR #2 的公开审核与 README 安装步骤核对，未声明本站独立安装实测。其余历史条目保留原收录出处，专项范围待补充。
